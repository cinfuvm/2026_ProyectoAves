= Extensiones propuestas al contrato de la API

== Contexto

El equipo mobile implementa el cliente HTTP contra `birds_apis.yaml` en
`mobile/lib/services/` (`auth_service.dart` y `fotos_service_bff.dart` con
su variante mock). La app ya habla contra estos endpoints; lo que sigue
pendiente es que el contrato declare lo que el cliente usa y que el
backend lo confirme antes de la integración final.

== 1. Endpoints que la app ya llama y el contrato no declara

[cols="1,1,3"]
|===
|Método |Ruta que usa la app |Uso

|GET |`/api/user/me` |Revalida la sesión JWT al arrancar
|DELETE |`/api/user/logout` |Cierra sesión en el servidor
|GET |`/images/reports` |Lista reportes para la pantalla de moderación
|PUT |`/images/reports/\{id}` |Cambia el estado de un reporte (solo rol `admin`)
|===

Además, el contrato declara las rutas como `/user/login` y `/user/signin`
mientras el cliente las llama bajo el prefijo `/api/`. Hay que acordar si
el prefijo lo añade el servidor o si debe figurar en el contrato.

== 2. `POST /images`: aceptar lugar, fecha y comentario

El RF-08 exige registrar el avistamiento con Lugar, Fecha, Comentario y
Fotografía. El cliente ya envía estos campos en `multipart/form-data`; el
contrato actual solo documenta `file` y `categoria`, así que la propuesta
es incorporarlos a la especificación.

[cols="1,3,1"]
|===
|Campo |Descripción |Requerido

|lugar |Lugar donde se observó el ave |no
|fecha |Fecha del avistamiento en formato `YYYY-MM-DD` |no
|comentario |Texto libre del observador (máx. 500) |no
|===

== 3. `GET /images`: devolver autor, lugar, fecha y comentario

Para el feed comunitario (RF-11) la app muestra quién subió la foto, dónde
y cuándo. El parser del cliente ya acepta estos campos; el schema `Imagen`
del contrato solo declara `id`, `url`, `categoria` y `subida_en`.

[cols="1,3"]
|===
|Campo |Descripción

|autor |Identificador público del usuario que subió la foto
|lugar |Lugar del avistamiento
|fecha |Fecha del avistamiento (`YYYY-MM-DD`)
|comentario |Comentario del observador
|===

== 4. `categoria` como enum cerrado

La app agrupa los órdenes taxonómicos en categorías generales. Para que
el filtro de `GET /images` y el campo de `POST /images` sean coherentes,
`categoria` debería ser un enum con valores en minúscula:

[cols="1,3"]
|===
|Valor |Categoría general

|terrestres |Terrestres
|acuaticas |Acuáticas
|rapaces |Rapaces
|marinas |Marinas
|otras |Otras
|===

La app envía y recibe estos valores (o sus formas con tilde/espacio),
y normaliza internamente con `categoriaGeneralAves`.

== 5. `GET /images`: filtro opcional por autor

Para poder consultar "mis fotos subidas" desde el perfil:

[cols="1,3,1"]
|===
|Parámetro |Descripción |Requerido

|autor |Identificador público del usuario |no
|===

== 6. Estados de reporte: hay que alinearlos

El contrato define el enum `recibido`, `en_revision`, `resuelto`,
`descartado` (`birds_apis.yaml:368-370`). La app y su pantalla de
moderación usan `abierto`, `revisado`, `descartado`
(`mobile/lib/models/reporte_moderacion.dart:52`,
`mobile/lib/screens/reportes_screen.dart:201-203`).

Hay que elegir un solo conjunto y actualizar la otra parte. Esta
discrepancia está documentada porque afecta directamente a la
integración del RF-14.

== 7. Motivos de reporte

La app envía los motivos del enum del contrato:

* `no_es_ave`
* `contenido_ofensivo`
* `imagen_enganosa`
* `derechos_autor`
* `otro` (con `detalle` libre de hasta 500 caracteres)

El detalle de la UI se mapea en `motivosReporteContrato`
(`mobile/lib/services/fotos_service.dart`).

== 8. Erratas en el esquema

* `confirm_pasword` aparece escrito así en dos lugares
  (`birds_apis.yaml:242` y `:257`); debería ser `confirm_password`.
  Si se corrige, avisar al equipo mobile porque la app lo serializa.
